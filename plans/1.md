# Implementation Plan: Execution Feasibility Ranker

## Overview

The Execution Feasibility Ranker is a **vector function** that evaluates multiple startup ideas simultaneously to produce a comparative ranking. Unlike scalar functions that score items in isolation, this function produces a probability distribution (scores summing to ~1) where each score represents relative execution feasibility compared to the alternatives presented.

**Function Type**: `vector.function`

---

## Input Schema

### Structure

```json
{
  "type": "object",
  "description": "A set of startup ideas to compare for relative execution feasibility",
  "properties": {
    "items": {
      "type": "array",
      "description": "Array of startup ideas to rank by execution feasibility",
      "items": {
        "anyOf": [
          {
            "type": "string",
            "description": "A text pitch describing a startup idea"
          },
          {
            "type": "image",
            "description": "A visual pitch (slide, mockup, diagram)"
          },
          {
            "type": "video",
            "description": "A video pitch"
          },
          {
            "type": "audio",
            "description": "An audio pitch"
          },
          {
            "type": "array",
            "description": "A composite pitch combining multiple modalities",
            "items": {
              "anyOf": [
                { "type": "string" },
                { "type": "image" },
                { "type": "video" },
                { "type": "audio" }
              ]
            }
          }
        ]
      },
      "minItems": 1
    }
  },
  "required": ["items"]
}
```

### Field Descriptions

- **items**: An array of startup ideas to compare. Each item can be:
  - A text string describing the startup concept
  - An image (pitch deck slide, mockup, diagram)
  - A video pitch
  - An audio pitch
  - A composite array combining multiple modalities for a single idea

---

## Input Maps

**No input maps are needed.** 

This function evaluates all items simultaneously in a comparative context rather than mapping over items individually. Each task receives the complete input (all items) and produces a comparative ranking across all of them. The comparative nature is fundamental—we're not scoring ideas in isolation but ranking them against each other.

## Tasks Design

Each task is a `vector.completion` that compares all startup ideas on a specific dimension. The system prompt establishes the evaluation criteria, the user content presents all items for comparison, and the responses represent ranked outcomes.

### Task Structure Pattern

For a vector function comparing N items, each task must:
1. Present ALL items in the user message
2. Define responses that represent comparative orderings or ratings
3. Output a vector of scores (one per item) from the probability distribution

## Expression Design

### User Content Expression

Each task needs to format all items for comparison. Using Starlark:

```starlark
"Compare these startup ideas for [DIMENSION]:\n\n" + "\n\n".join([
  "IDEA " + str(i+1) + ": " + (str(item) if type(item) == "string" else "[Multimodal content]")
  for i, item in enumerate(input['items'])
])
```

For multimodal content, we'll need to handle arrays by including all content types.

### Response Design

For comparative ranking, responses should identify which ideas rank highest/lowest on each dimension. With dynamic item counts, we need responses that work for any N:

**Approach**: Use responses that identify relative rankings, then compute scores from the probability distribution.

Example responses for a dimension:
```json
[
  "IDEA 1 is most feasible on this dimension",
  "IDEA 2 is most feasible on this dimension",
  "IDEA 3 is most feasible on this dimension",
  ...
]
```

The output scores from `vector.completion` directly give us the probability each idea is "most feasible" on that dimension.

### Output Expression

For each task, the output is the raw scores vector since it already represents comparative probabilities:

```starlark
output['scores']
```

### Final Aggregation

The function aggregates across 14 tasks with equal pillar weighting:
- Pillar I (Tasks 1-4): 25% weight → each task 6.25%
- Pillar II (Tasks 5-7): 25% weight → each task 8.33%
- Pillar III (Tasks 8-10): 25% weight → each task 8.33%
- Pillar IV (Tasks 11-14): 25% weight → each task 6.25%

The final output normalizes the weighted sum to ensure it sums to ~1.

---

## Dynamic Response Generation Challenge

**Key Challenge**: The number of items is dynamic, but `vector.completion` requires fixed response options.

**Solution Options**:

1. **Fixed Maximum Items**: Define responses for up to N items (e.g., 10) and pad/truncate. Not ideal.

2. **Pairwise Comparisons**: Use mapped tasks to compare pairs, then aggregate. Complex.

3. **Holistic Ranking Responses**: Use responses like "The ideas rank as follows from most to least feasible: [ordering]" - but this creates factorial response options.

4. **Per-Dimension Binary**: For each dimension, ask "Which idea is MOST feasible?" with one response per item, letting the probability distribution handle the ranking.

**Recommended Approach**: Option 4 - Create dynamic responses based on input length where each response identifies one idea as "most feasible" on that dimension. The probability distribution over these responses directly gives us the comparative ranking.

**Implementation**: The responses array must be constructed dynamically based on `input.items.length`. This requires understanding if the schema supports dynamic response generation via expressions.

If dynamic responses aren't supported, we'll need a hybrid approach:
- Define a reasonable maximum (e.g., 10 items)
- Use responses like "IDEA 1 is most feasible", "IDEA 2 is most feasible", etc.
- Filter/normalize based on actual item count in output expression

## Implementation Notes

1. **Function Type**: Must be `vector.function` not `scalar.function`

2. **Response Dynamics**: Each task's responses must handle variable item counts. Consider using a maximum of 10 items with responses "IDEA 1 is most feasible on this dimension" through "IDEA 10..."

3. **Output Normalization**: Final aggregation must normalize to sum to ~1

4. **Multimodal Handling**: User content construction must handle strings, images, videos, audio, and arrays (composite pitches)

5. **Pillar Weighting**: Implement as weighted average across tasks:
   - Tasks 1-4: weight 0.0625 each (25% / 4)
   - Tasks 5-7: weight 0.0833 each (25% / 3)
   - Tasks 8-10: weight 0.0833 each (25% / 3)
   - Tasks 11-14: weight 0.0625 each (25% / 4)

6. **Score Interpretation**: Higher scores = more feasible = easier to execute
