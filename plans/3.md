# Implementation Plan: Execution Feasibility Ranker

## Overview

This plan describes the implementation of the `execution-feasibility-ranker`, a **vector.function** that takes an array of startup ideas (in various formats) and produces a probability distribution ranking them by relative execution feasibility.

---

## 1. Input Schema Structure

The input schema follows the SPEC.md exactly:

```json
{
  "type": "object",
  "description": "An array of startup ideas to compare for relative execution feasibility",
  "properties": {
    "items": {
      "type": "array",
      "description": "Two or more startup ideas to rank. Each idea can be text, image, audio, video, or a composite array combining multiple formats.",
      "minItems": 2,
      "items": {
        "anyOf": [
          {
            "type": "string",
            "description": "A text pitch or description of a startup idea"
          },
          {
            "type": "image",
            "description": "An image representing a startup idea (mockup, diagram, prototype photo)"
          },
          {
            "type": "audio",
            "description": "An audio pitch or demonstration of a startup idea"
          },
          {
            "type": "video",
            "description": "A video pitch or demonstration of a startup idea"
          },
          {
            "type": "array",
            "description": "A composite representation combining multiple formats for a single startup idea",
            "minItems": 1,
            "items": {
              "anyOf": [
                {"type": "string"},
                {"type": "image"},
                {"type": "audio"},
                {"type": "video"}
              ]
            }
          }
        ]
      }
    }
  },
  "required": ["items"]
}
```

### Field Descriptions

| Field | Type | Description |
|-------|------|-------------|
| `items` | array | Required. Array of 2+ startup ideas to compare. |
| `items[n]` (string) | string | A text-based startup pitch or idea description |
| `items[n]` (image) | image | Visual representation (mockup, diagram, prototype) |
| `items[n]` (audio) | audio | Verbal pitch or audio demonstration |
| `items[n]` (video) | video | Video pitch or product demonstration |
| `items[n]` (array) | array | Composite: multiple formats for one idea |

## 2. Output Configuration

### Output Length
Dynamic based on input size:
```json
{
  "$starlark": "len(input['items'])"
}
```

### Output Type
Vector of probabilities summing to approximately 1, where higher values indicate higher relative execution feasibility.

---

## 3. Input Maps

**No input maps are needed** for this function. 

The function requires **simultaneous comparative evaluation** of all ideas together, not individual scoring that gets aggregated. Each task must see all items at once to produce meaningful relative rankings.

This is because:
1. Feasibility is inherently comparative (an idea's feasibility depends on what it's being compared to)
2. The output is a probability distribution requiring normalization across all items
3. Separate scoring would lose the comparative context essential to the philosophy

```json
{

  "input_schema": { /* as defined above */ },
  "output_length": {"$starlark": "len(input['items'])"},
  "tasks": [
    /* 18 evaluation tasks across 4 pillars */
    /* 1 synthesis task to produce final ranking */
  ]

```

## 5. Task Implementation Strategy

### Approach: Comparative Completion Tasks

Each task will use `vector.completion` to evaluate all ideas simultaneously. The system prompt will instruct the model to compare ideas and the responses will represent comparative rankings.

### Task Structure Pattern

For each evaluation dimension, we use a task that:
1. Presents ALL ideas to the model simultaneously
2. Asks it to rank them comparatively on the specific dimension
3. Uses response options that map to relative rankings
4. Outputs a score for EACH idea via weighted response probabilities

### Dynamic Content Construction

Since the number of items is variable (2+), we need to dynamically construct the prompt content. This requires building a numbered list of all items in the user message.

---

## 6. Expressions Needed

### 6.1 Constructing Item Lists for Prompts

To present all ideas in a single prompt, we need to enumerate them:

```starlark
# Build numbered list of all items for prompt
'\n'.join(['Idea ' + str(i+1) + ': ' + str(item) for i, item in enumerate(input['items'])])
```

**Note**: For multimodal items (images, audio, video), we may need structured content arrays rather than string concatenation. The approach will depend on how the runtime handles multimodal content in prompts.

### 6.2 Response to Score Mapping

For binary comparative responses per idea:
```starlark
output['scores'][1]  # Score for "high feasibility" response
```

For multi-level responses (e.g., 5-level scale):
```starlark
output['scores'][0] * 1.0 + output['scores'][1] * 0.75 + output['scores'][2] * 0.5 + output['scores'][3] * 0.25 + output['scores'][4] * 0.0
```

### 6.3 Output Length Expression
```starlark
len(input['items'])
```

## 7. Detailed Task Definitions

### Pillar 1: Technical Feasibility

#### Task 1.1: Technology Readiness
- **System**: Evaluate technology maturity for each startup idea
- **User**: Present all ideas, ask to compare technology readiness
- **Responses**: Scale from "proven/off-the-shelf" to "requires breakthrough"
- **Output**: Higher score = more ready technology

#### Task 1.2: Integration Complexity
- **System**: Evaluate system integration complexity
- **User**: Compare ideas on integration challenges
- **Responses**: Scale from "simple/self-contained" to "complex novel integration"
- **Output**: Higher score = simpler integration

#### Task 1.3: Talent Availability
- **System**: Evaluate accessibility of required talent
- **User**: Compare ideas on talent requirements
- **Responses**: Scale from "generalists can build" to "requires rare specialists"
- **Output**: Higher score = more available talent

#### Task 1.4: Infrastructure Dependency
- **System**: Evaluate infrastructure dependencies
- **User**: Compare ideas on infrastructure requirements
- **Responses**: Scale from "works today" to "awaits future infrastructure"
- **Output**: Higher score = less dependency

### Pillar 2: Resource Requirements

#### Task 2.1: Capital Intensity
- **Responses**: Scale from "bootstrappable" to "massive capital required"
- **Output**: Higher score = lower capital needs

#### Task 2.2: Team Size/Specialization
- **Responses**: Scale from "solo/small generalist team" to "large specialized org"
- **Output**: Higher score = smaller/simpler team

#### Task 2.3: Time to Market
- **Responses**: Scale from "months" to "years"
- **Output**: Higher score = faster to market

#### Task 2.4: Partnership Dependency
- **Responses**: Scale from "direct to customer" to "requires many gatekeepers"
- **Output**: Higher score = less partnership dependency

### Pillar 3: Regulatory Complexity

#### Task 3.1: Regulatory Burden
- **Responses**: Scale from "unregulated" to "heavily regulated"
- **Output**: Higher score = lighter regulation

#### Task 3.2: Regulatory Clarity
- **Responses**: Scale from "clear stable rules" to "uncertain/changing"
- **Output**: Higher score = clearer rules

#### Task 3.3: Geographic Variation
- **Responses**: Scale from "globally uniform" to "fragmented by jurisdiction"
- **Output**: Higher score = simpler geography

#### Task 3.4: Compliance Cost
- **Responses**: Scale from "minimal overhead" to "continuous expensive compliance"
- **Output**: Higher score = lower cost

### Pillar 4: Execution Risk Profile

#### Task 4.1: Go-to-Market Clarity
- **Responses**: Scale from "obvious path" to "complex/unproven"
- **Output**: Higher score = clearer GTM

#### Task 4.2: Market Validation
- **Responses**: Scale from "proven demand" to "category creation"
- **Output**: Higher score = more validated

#### Task 4.3: Competitive Positioning
- **Responses**: Scale from "underserved niche" to "entrenched incumbents"
- **Output**: Higher score = better positioning

#### Task 4.4: Operational Complexity
- **Responses**: Scale from "pure software" to "complex physical ops"
- **Output**: Higher score = simpler operations

#### Task 4.5: Iteration Speed
- **Responses**: Scale from "rapid iteration" to "long locked-in cycles"
- **Output**: Higher score = faster iteration

#### Task 4.6: Network Effect Bootstrapping
- **Responses**: Scale from "no network effects needed" to "severe cold start"
- **Output**: Higher score = less network dependency

### Synthesis Task

#### Task 5.1: Holistic Feasibility Ranking
- **System**: Synthesize all dimensions into final comparative ranking
- **User**: Present all ideas with context from prior evaluations
- **Responses**: Probability distribution across ideas
- **Output**: Final normalized scores

## 8. Implementation Challenge: Multimodal Comparative Prompts

A key challenge is constructing prompts that present multiple multimodal items for simultaneous comparison. Options:

### Option A: Serialize to Descriptions
Convert all items to text descriptions first, then compare. Loses richness of images/video.

### Option B: Structured Content Arrays
Use message content arrays with multiple items:
```json
{
  "role": "user",
  "content": [
    {"type": "text", "text": "Compare these ideas for technical feasibility:"},
    {"type": "text", "text": "Idea 1:"},
    {"$starlark": "input['items'][0]"},
    {"type": "text", "text": "Idea 2:"},
    {"$starlark": "input['items'][1]"}
    // ... dynamically for all items
  ]
}
```

### Option C: Per-Item Tasks with Aggregation
Evaluate each item individually, then aggregate. Loses comparative context.

**Recommended**: Option B where possible, with fallback logic for complex composites.

## 10. Validation Criteria

1. **Sum Constraint**: All output vectors should sum to approximately 1.0 (±0.05)
2. **Ordering Consistency**: Clear feasibility differences should produce clear score differences
3. **Comparative Stability**: Adding a third idea shouldn't dramatically change relative ranking of first two
4. **Multimodal Parity**: Same idea expressed in different formats should score similarly
5. **Dimension Coverage**: All four pillars should influence final scores

2. **Score Aggregation**: Should individual pillar scores be averaged, or should the synthesis task weight them dynamically based on context?
